# 训练过程说明 0624

## 1. 为什么有时只看到两帧

- 当前训练可视化页不是直接把 8 帧原始 context video 全部铺开，而是按 `latent_frames` 做对齐后再渲染。
- 在 `inspect_train_aux_losses_v_newtrain_compare.py` 里，`_render_box_overlay(...)` 和 `_render_track_overlay(...)` 都先取 `latent_frames = gt_box_xyxy.shape[0] / gt_track_summary.shape[0]`，然后把每个 latent step 映射回一帧代表图。
- 当 8 帧 context 经过 VAE 时间压缩后只对应 2 个 latent step 时，页面就只会显示 2 帧代表图，不是原视频只剩 2 帧。
- 当前实现里，如果 `source_frames % latent_frames == 0`，会取每个组里的最后一帧做代表帧，所以 8 帧上下文常会显示成 2 帧。

## 2. 黄色点、蓝色点、黄色框、蓝色框分别是什么

- `inspect_train_aux_losses_v_newtrain_compare.py`
  - `GT track` 是橙色
  - `Pred track` 是蓝色
  - `GT box` 是红色
  - `Pred box` 是青绿色
- 也就是说，这个训练 loss 对比页里，颜色语义是固定的 `GT / Pred`，不是对象编号颜色。
- 这页本身没有“黄色框/黄色点”的语义；如果你在浏览器里看到偏黄的点，一般是橙色 `GT track` 在视频编码/浏览器显示下看起来更接近黄色。
- 如果你看到的是多对象可视化页 `eval_vggt_sam_multi_object_viewer.py`
  - 每个 object slot 会用自己的对象颜色
  - 黄色、蓝色这类颜色只是不同对象槽位的区分
  - `fix` 标记的黄色点 `(255,255,0)` 表示被 correction step 修正后的轨迹点，不是 GT
  - 这个页面里的 `GT box` 仍然是白色，`pred/sam` box 才是对象槽位颜色

## 3. 这次异常的初步结论

- 当前 `pybullet0624_diffsynth_object_v_newtrain_gpu67` 的异常更像是“对象 prior / track 对齐”出了问题，而不是单纯 loss 权重不够。
- 现象包括：
  - `train/object_context_abs_max` 持续变大
  - `pred box` 明显偏大，且左上角偏移明显
  - `pred track` 和 `GT track` 位置不一致
  - 可视化里有一些点落到画面左上角
- 后续需要重点核查：
  - query prior 是从哪一帧采样出来的
  - CoTracker 的 query frame id 是否和 prior 来源帧一致
  - object summary 到 box 的回归是否在奖励“贴近左上角的退化解”

## 3.1. 新确认的根因

- 这次进一步核实后，最关键的问题不是单纯的 `loss` 权重，而是训练链路里**query 起始帧语义和 CoTracker 解释不完全一致**。
- `train_v_newtrain.py` 里确实已经构造了 `query_frame_ids`，但正式训练以前这一路如果不显式传入 CoTracker，就会让“query 是从哪一帧采样的”和“tracker 认为 query 从哪一帧开始”出现错位。
- 这种错位会直接导致：
  - `pred track` 在时间上被拉歪
  - 由 track 聚合出来的 `active_track_summary` 偏移
  - `pred box` 继承错误的中心和尺寸先验
  - `object_context_abs_max` 被放大，因为 object token 在吸收错误几何后变得更激进
- 这个问题和 `object_context_abs_max` 本身不是同一个层面：
  - `object_context_abs_max` 只是结果监控
  - 真正需要修的是 query 起点、track 聚合和 box prior 的一致性

## 3.2. 当前处理方式

- 已经把正式训练入口里的 CoTracker 调用对齐到 smoke 路径，显式传入 `query_frame_ids`。
- 另外把 `object_context` 的监控从单一 `abs_max` 扩展成：
  - `train/object_latent_tokens_abs_max`
  - `train/object_context_abs_max`
  - `train/object_context_abs_mean`
  - 这样后面如果 `abs_max` 继续抖大，我们能区分：
  - 是少量 token 的极值异常
  - 还是整条 object context 分支系统性变强

## 3.3. 这次复核后确认的漏洞

- 之前 `ObjectTubeProjector._boxes_from_tracks(...)` 虽然接收了 `box_prior_xyxy`，但在“存在有效 track”时仍然优先返回 `active_box_xyxy`
  - 这等价于仍然让 box 基座主要由 track 的极值框决定
  - `box_prior_xyxy` 只在无效 slot 才真正生效
- 这会导致两个问题
  - 如果 track 里有少量左上角漂移点，`active_box_xyxy` 仍会跟着偏
  - `ObjectAuxHeads` 的 box 回归又会围绕这个偏掉的 base 继续修正，容易把中心和尺寸一起带歪
- 这次已经把它改成
  - 有有效 track 时优先使用 `box_prior_xyxy` 作为 box anchor
  - track 只负责提供聚合特征和 residual 校正
  - `ObjectAuxHeads` 的 box center 也改成跟随当前 `track summary`，box 尺寸则继承 prior 的宽高

## 3.7. 新确认的坐标系问题

- 进一步核查后，当前的明显偏移更像是坐标变换不一致，而不是数据本身的 box 写错
- 证据
  - `context_boxes` 本身的首帧和末帧 box 都在图像中间偏右中下，并不在左上角
  - 但 `pred track center` 和 `pred box center` 仍然明显偏左上
  - 说明问题更像是 CoTracker 输出回到 native 分辨率时的缩放方式，以及训练/可视化脚本对轨迹坐标的解释不完全一致
- 已做修正
  - `CoTrackerAdapter._scale_tracks(...)` 改成和分析脚本一致的 `align_corners` 风格比例映射
  - `ObjectTubeProjector._resize_tracks_xy(...)` 统一成同类比例映射
- 这一类修正的目标
  - 避免同一条轨迹在不同模块里被当成不同坐标系
  - 减少“所有点都往左上跑”的系统性偏移
  - 让后续的 track / box residual 只学真实运动，不学坐标系误差

## 3.11. 最新复核：当前异常更像“监督约束不够硬”，不是单点数值爆炸

- 最近重新核查后，当前问题可以拆成三层：
  - `train/object_context_abs_max` 不是根因，它只是 object condition 进入 Wan 主干后的结果统计
  - 真实几何监督里，`track_box_loss` 和 `track_iou_loss` 之前只作为监控项，没有进入总 loss，所以 track/box 只能“看起来对齐”，不能被硬约束住
  - 由于当前样本只有 1 个有效 object，其余 object slot 都是无效槽位，如果可视化不显式遮掉无效槽位，就很容易在左上角看到一些“假点/假框”
- 这次复核后的结论是：
  - `context_boxes` 本身并没有整体偏到左上
  - `active_prior` 也没有明显跑飞
  - 真正偏的是 `pred_track_summary` 和 `pred_box_xyxy`
  - 其中一部分来自 object head residual，一部分来自监督项不够硬

## 3.12. 本轮最小修正

  - 训练和对比可视化中，`object_valid_mask` 会被显式使用，无效 object slot 的 `pred box/track` 不再继续画出来干扰判断
- 这样做的目标：
  - 让几何监督不再只是“旁路监控”
  - 避免无效槽位在页面左上角制造假象
  - 让新的 smoke 更准确地反映有效 object 的真实轨迹和 box

## 3.13. 当前建议的 loss 设计

- 保持主损失不变：
  - `loss_main`
- 保留已有辅助项：
  - `lambda_track_aux * track_aux_loss`
  - `lambda_box_aux * box_aux_loss`
  - `lambda_depth_aux * depth_aux_loss`
- 新增轻量几何约束：
  - `lambda_track_box_aux * track_box_loss`
  - `lambda_track_iou_aux * track_iou_loss`
- 建议初始值仍然保守：
  - `lambda_track_box_aux = 0.01 ~ 0.02`
  - `lambda_track_iou_aux = 0.01 ~ 0.02`
- 这样不会把几何 loss 变成主导项，但能防止 track/box 完全漂移到不合理区域

## 9. 当前 root cause 重新整理

- `train/object_context_abs_max` 现在统计的是 `ObjectConditionAdapter` 的输出，不是原始 `object_latent_tokens`
- 这条分支在当前实现里是
  - `object_latent_tokens + slot_embed + time_embed`
  - `LayerNorm`
  - `residual MLP`
  - `LayerNorm`
  - `object_valid_mask`
- 所以 `object_context_abs_max` 变大不一定是数值错误，但如果它持续增长，通常表示 object 条件在主干里变得更强，且可能开始放大错误几何信号
- 当前 box / track 偏移的更大嫌疑来自几何 prior，而不是 `object_context_abs_max` 本身
  - `track -> box` 之前用的是全部点的极值框，容易被少量漂移点拉大
  - `ObjectAuxHeads` 又把这个 prior 当作 box residual 的基座
  - 如果 prior 本身左上偏、又偏大，预测 box 很容易沿着这个偏差继续修正不回来
- `track_box_loss` 和 `track_iou_loss` 之前只作为日志，不会直接推动优化器修正 track/box 几何

## 10. 当前修复方向

- 已做的代码修正
  - `ObjectConditionAdapter` 增加最终 `out_norm`
  - `ObjectTubeProjector._boxes_from_tracks(...)` 改成更稳的 trimmed prior，并加了最小 box 尺寸底线
  - `train_v_newtrain.py` 新增可选几何损失参数：
    - `lambda_track_box_aux`
    - `lambda_track_iou_aux`
  - 默认值仍然是 `0.0`，不会破坏旧 run

  - 再开一个正式 run
  - 先用很小的几何损失权重，例如

  - 观察 `pred box` 是否开始收敛到更合理的 size 和 center
  - 观察 `pred track` 是否还会往左上角漂

## 15. v6 方案修正

    - box prior 的最小尺寸 floor 提高到 `16px`
